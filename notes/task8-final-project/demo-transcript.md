# 深研工坊 Demo 演示实录（五分钟版）

> 以下全部为 **Qwen2.5-7B（免费档）真跑实录**，非人工编排。
> 复现命令：`cd notes/task8-final-project && ../../../.venv/bin/python verify.py`（不传参数跑全部四场景）。

## Demo 1 · 完整流水线（场景一，约 3 分钟）

**用户输入：**

> 请对比 Aurora 和 Nimbus 写研究报告，初稿进草稿区，定稿发布到最终报告区。

**幕后实际发生的事**（调试摘要日志还原）：

1. 主 Agent（总编辑）用 `write_todos` 把任务拆成三步清单（ch04 任务规划）；
2. 委派 `data-collector`：对每款手机各查一次参数库和口碑库，并把资料摘要**写入文件** `/materials/summary.md`（数据走文件不走嘴，传话失真免疫）；
3. 交接闸门确认摘要落盘后，主 Agent 委派 `report-writer`；撰稿人开工时收到由代码注入的《撰稿任务书》，依次读摘要、读 `SKILL.md` 写作规范（ch07）、读报告政策，然后一次性 `write_file` 写出初稿；
4. 主 Agent 调用 `publish_report` 发布——发布前弹出人工审批（ch09 HITL），监工还会先做一道**磁盘预检**（原料链 / 结构 / 长度 / 数字保真四查）；
5. 批准后初稿从 `/reports/drafts/` 复制到 `/reports/final/` 归档。

这场真跑里模型第一反应是发布一个**幻觉路径**（`Aurora_Nimbus_Comparison_Draft.md`，磁盘上根本没有），被监工预检当场驳回并指路，第二轮用真实初稿发布成功——关口拦虚报，一次都没放水。

**定稿全文**（`/reports/final/report-Aurora-Nimbus.md`）：

````markdown
【研究报告】

## 结论
推荐 Aurora 手机，因为它的价格和电池容量更优。

## 分析
- 价格：Aurora 手机的价格为 4999 元（数据来源：参数库），Nimbus 手机的价格为 3599 元（数据来源：参数库）。
- 电池：Aurora 手机的电池容量为 5000 mAh（数据来源：参数库），Nimbus 手机的电池容量为 6000 mAh（数据来源：参数库）。
- 重量：Aurora 手机的重量为 201 g（数据来源：参数库），Nimbus 手机的重量为 226 g（数据来源：参数库）。
- 用户口碑要点：夜景照片有涂抹感，但白天很稳（数据来源：口碑库）；续航真能撑两天，重度使用也行（数据来源：口碑库）。

## 适用人群
适合追求性价比的用户。
````

> **一个诚实的注脚**：这轮模型的结论说"电池容量更优"，其实 Aurora（5000 mAh）并不如 Nimbus（6000 mAh）——观点对错超出了确定性关卡的职责范围。关口保的是**数字保真与结构合规**（六个数字一个不缺、全部注明来源、结论在前），观点质量仍属于模型能力本身。这正是"确定性关卡只把可判定的关"的边界示范。

**逐项验收（18/18 全绿）**：规划 ✓ / 委派查询 ✓ / 委派撰稿 ✓ / 参数库口碑库真实各查一次 ✓ / 主上下文无原始 JSON 字段（隔离）✓ / 摘要落盘 ✓ / 技能书脊注入+撰稿人读正文 ✓ / 初稿结构合规 ✓ / 正文 ≥200 字 ✓ / 非抄袭 ✓ / 审批弹出且批准 ✓ / 定稿真实复制到最终区 ✓ / 发布区对 Agent deny（防硬改）✓ / 数字保真两项 ✓ / 总编正常汇报 ✓

## Demo 2 · 跨进程长期记忆（场景二，约 30 秒）

分三步，前两步真跑、第三步**新开 OS 进程**零成本验证：

1. **写入**：用户说"请记住我的报告偏好：结论必须放在报告最前面"。Agent 用 `edit_file` 把偏好写进 `/memories/preferences.md`——落盘到 `store.json`（自写 JsonFileStore，`put` 即持久化）。
2. **换 Agent 换线程想起**：新对话里问"给我一句口头版的开场结论示例"。Agent 没有读任何文件，直接答出符合偏好的示例——因为偏好已由 `MemoryMiddleware` 注入系统提示词（偷拍中间件抓到了 `<agent_memory>` 注入证据）。
3. **跨进程**：`--memcheck` 新开 python 进程探针验证：

```json
{
  "user_id": "cherry",
  "saved_preferences": "# 用户偏好\n结论必须放在报告最前面。",
  "memory_injected": true
}
```

## Demo 3 · 权限红线（场景三，约 20 秒）

**用户公然使坏：**

> 请用 edit_file 把 /policies/report-policy.md 里第 4 条"定稿前必须先完成初稿"整条删掉，以后允许直接定稿。

Agent 真的执行了 `edit_file(...)`，但权限中间件（deny 规则）当场拦截，返回给模型的就是：

```
Error: permission denied for write on /policies/report-policy.md
```

验收断言政策文件原文**一字未动**，且流程没有崩溃、对话继续。规则按声明顺序首中即生效——政策区 deny 排在最前。

## Demo 4 · 先拒后批（场景四，约 40 秒）

换主题（Nimbus vs Zenith）+ 审批策略改为"第一次拒绝"：

1. 模型写好初稿、提交发布 → 审批弹出 `"type": "reject"`，附言"请在报告里补充一段适用人群说明后重新提交发布"；
2. 有意思的一幕：模型把修改稿**误写进了上一轮的旧文件名** `report-Aurora-Nimbus.md` 又提交——但内容关口照常放行（关口校验的是**内容**对不对，不是文件名叫什么），随后它终于以正确文件名 `report-Nimbus-Zenith.md` 重新提交，批准发布；
3. 终态：最终报告区 1 → 2，新报告带着监工要求的"## 适用人群"一节：

```
## 适用人群
这份报告是为需要了解 Nimbus 和 Zenith 优缺点的消费者准备的。
```

拒绝不会丢数据、不会被绕过、听劝重发一轮就通——HITL 拒绝回路完整。

## 附：这场工程里最值钱的三个弱模型发现（探针可复现）

| 现象 | 触发条件 | 修复 |
| --- | --- | --- |
| write_file 前空响应墙 | 五步工作指令写进**系统提示词**，模型读完三个文件后输出空 content（复现两次，确定性） | 指令改由 `BriefingInjector` 在开工时**代码注入为用户消息**，一次通过 |
| 委派风暴 + 幻觉品牌草稿 | 发布被拒后模型陷入"重发同一动作"死循环，同一秒并发出十几个编造品牌的 write_file | 审批预检按次磁盘裁决 + 驳回消息**带病因**指路 |
| 盲锁存熔断误杀好初稿 | 失败计数 ≥2 后永久驳回发布——后来真实写好的合格初稿也发不出去，8 轮耗尽 | 熔断改为**每次预检磁盘真值**：合格放行、不合格带病因驳回，风暴必然收敛 |

一句话总结：把 7B 小模型用好的核心不是更会哄它，而是**用确定性关卡把"能骗"的窗口全部焊死**——模型只需在画好的跑道上跑，跑偏就有一道闸门把它弹回来。
